## 1. XLS-27 — 0 件テーブルの申し送り（対象 PJ・解説書担当宛）

出典: `issues.md:2913-2982`

**旧文面（変換不能という制約）は撤回済み。** 番人は撤去済みで、変換は止まらない。伝えるべきは以下のみ。

**宛先1: 対象 PJ（変換ツール利用者）**

- 対象はテーブル系4データタイプのみ（`SETUP_TABLE`／`EXPECTED_TABLE`／`EXPECTED_COMPLETE_TABLE`／`LIST_MAP`）。ファイルデータ・メッセージは対象外。
- Excel の0件テーブルが持つカラム名は、YAMLへ変換すると失われる（`rows: []` にはカラム名を書く場所が無い）。警告は出ない。
- Excel → YAML → Excel と戻すと、カラム名の代わりに `[EMPTY]` という列が1つだけ現れる。元のカラム名は復元されない。
- この `[EMPTY]` 列を消してはならない（消すとカラム名の行自体が無くなり、次の行がカラム名として誤読される）。
- `[EMPTY]` という語は明文が定めたものではなく converter が選んだ語（明文が定めるのは「半角角括弧 `[ ]` で囲むとマーカーカラムになる」ことだけ＝ `notation:1515`）。

**宛先2: 解説書担当（`nablarch-document`）**

- カラム名を持たない0件テーブルをExcelでどう書くかが、明文の1箇所では述べられていない。`notation:789`（カラム名を持つ0件テーブルの記述例）・`:836`・`:802`・`:1515` の3箇所を突き合わせて初めて「マーカーカラムを1つ置く」と導ける。明記されると読み手が導出せずに済む。
- 行番号は `30a8271` 時点。`fd2e44d` 時点では `:1515`／`:1550` がそれぞれ `:1514`／`:1549` へ1行ずれている（`:789`・`:802`・`:819`・`:836`・`:881`・`:883`・`:1134-1138`・`:1143`・`:1146`・`:1158` は不変。ただし `:836`・`:1143` は文面に空白エスケープの差あり。実測2026-08-21）。

## 2. XLS-39 — グループ ID に使える文字の明文化（解説書担当・本体スキーマ担当宛）

出典: `issues.md:3772-3789`

**依頼**: グループ ID に使える文字を明文で定めてほしい。とくに、Excel 形式が区切りに使う `[` ／ `]` をグループ ID の値に含められるかどうか。

**なぜ要るか**: 解説書はグループIDの書き方（`notation:278`）と収集規則（`notation:269`）を定めるだけで文字種に触れておらず、本体スキーマの `group_id` も4箇所すべて `minLength: 1` のみで文字種の制約が無い（2026-08-19実測）。そのため `group_id: "[a]x[b]"` はスキーマ適合の入力でありながら、Excel形式へ書き出すと `SETUP_TABLE[a]x[b]=` になり、YAMLへ書き戻すと `a]x[b` という別のグループになる。

**決着すると何が決まるか**:
- 「区切り文字は使えない」と定まる場合 → converterは中間モデルの生成時に拒否できる（あわせてスキーマ側に `pattern` を足すことが要る）。
- 「使える」と定まる場合 → 辺④の `YamlFormatWriter.java:479-488` の `rawGroup` が外側1組を外す挙動が不具合になる。

**converter側の現状**: 番人は置いていない。判定は保留のまま。

## 3. XLS-40 — テーブル系のカラム名の大小の扱いの明文化（解説書担当・本体スキーマ担当宛）

出典: `issues.md:3889-3911`

**依頼**: テーブル系のカラム名の大小をどう扱うかを明文で定めてほしい。
1. 大文字化するのか、大小を区別するのか。
2. 大文字化するなら、大文字化後に同名となるカラムを「重複」としてエラーにするのか、後勝ちにするのか。

**なぜ要るか**: 解説書はカラム名を「最初の行のキーで決まる」（`notation:819`）とだけ定め、大小の扱いに触れていない。スキーマの `$defs.table_data.properties.rows.items` もキーの大小・一意性に制約を置いていない。そのため `{id: "1", ID: "2"}` はスキーマ適合の入力でありながら、本体 `TableData` の大文字化（`nablarch-testing` `65911f5` の `:97`／`:492`／`:530`）で `columnNames` ＝ `[ID, ID]` に潰れ、`id` に書いた値が警告も例外もなく消える（XLS-40・YML-10）。同じ記法で書いた `LIST_MAP` は大小を保ち両方の値が残るため、記法上は同じ書き方が経路によって違う結果になっている。

**決着すると何が決まるか**:
- 「大小を区別する」と定まる場合 → 本体 `TableData` の大文字化が不具合になる（修正先は `nablarch-testing`）。converterは `@Ignore` を外すだけでよい。
- 「大文字化する」と定まる場合 → さらに2の決着が要る。重複をエラーとするなら大文字化を行う本体側で検出するのが筋（converterは中間モデルの生成時に拒否できる）。後勝ちとするなら値が消えることが仕様になり、converter側の対応は不要（XLS-40のカラム名側は「対応不要」へ倒れる）。

**converter側の現状**: 番人もWARNも置いていない。**あるべき姿を主張する `@Ignore` つきテストは2026-08-28に削除した**（解説書に無い書き方は追わないため。#35）。現状を固定するテスト `YamlFormatReaderInvalidInputTest#dropsValueWhenTableColumnNamesDifferOnlyByCase` は残っている。決着すれば、そのテストの期待値を書き換えることになる。

## 4. XLS-42／YML-14 — 「フィールド数より値が少ない／多い行」の扱いの明文化（解説書担当・本体スキーマ担当宛）

出典: `issues.md:3956-3994`, `issues.md:4042-4069`

> `testdata_notation.rst:883` と `ntf-testdata-yaml-schema.json` の `$defs.record_fragment.rows` が、「データ行の要素数がフィールド定義の件数より少ない場合」について正反対を定めている。
> 前者は「不足したフィールドは `""` として補完される」とし、`rows:` に空配列 `[]` を書く使い方まで案内している。後者は「件数が一致しない場合はNTFがエラーを出す」としている。
> どちらが正かを決めて、両方の記述をそろえてほしい。
>
> あわせて、フィールド定義の件数より値が多い行の扱いも明文で確認したい。
> `notation:891` は記述時エラーとして「データ要素数が不正である」を挙げるが、本体パーサは実際にはエラーにせず、余りの値を黙って捨てる（2026-08-19実測。`fields` 1件のレコードに `rows: [["a","b","c"]]` を書くと、保持されるのは `a` だけで `b`・`c` は消える。辺②の入力経路。帰属は `nablarch-testing` の `DataFileFragment#addValue` ＝ converterの外）。
> エラーにするのか、黙って捨てるのが正なのかを明文化してほしい。

**converter側の現状**:
- 少ない側（XLS-42）: `notation:883` 側に立ち、少ない側を通す暫定の立ち位置（判定は保留。スキーマ側で決着した場合は担保テスト `RecordLayoutTest#フィールド定義の件数より要素数が少ないデータ行は保持できる` が赤になる）。
- 多い側（YML-14）: 帰属はconverterの外（本体パーサが余りを捨てる）。判定は「対応不要＝帰属がconverterの外」。**あるべき姿を主張する `@Ignore` つきテストは2026-08-28に削除した**（#35）。根拠にしていた `notation:891` の記述時エラー一覧は、現行の解説書（`5783b35`）に存在しない。現状を固定するテスト `YamlFormatReaderInvalidInputTest#dropsRecordFragmentValuesBeyondFieldCount` は残っている。
